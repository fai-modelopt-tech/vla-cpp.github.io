vla.cpp: A Unified Inference Runtime for Vision-Language-Action Models

A unified C++ runtime built on ggml and llama.cpp that serves eleven VLA policies, iterative and regression heads alike, from self-contained GGUF bundles on CUDA, Metal, CPU, SYCL, and OpenVINO, from desktop GPUs down to an 8 GB Jetson Orin Nano.

Abstract

Deploying vision-language-action (VLA) models on robots requires adapting model-specific inference pipelines to heterogeneous processors and limited onboard memory. We present vla.cpp, a unified C++ inference runtime for eleven VLA models. The runtime shares model loading, tensor execution, and serving while retaining architecture-specific attention, conditioning, and action heads. Iterative policies reuse observation-dependent computation across solver steps; regression policies use a direct prediction path.

We evaluate task success on LIBERO-Object and profile supported configurations on NVIDIA, Apple, and Intel hardware. BitVLA completes 200/200 LIBERO-Object episodes on an 8 GB Jetson Orin Nano; a separate desktop measurement records 1.3 GiB of device memory. A ternary tensor-core kernel accelerates its client inference by 4.0-4.6x over the CUDA-core baseline on RTX 3060 and AGX Orin. A SmolVLA case study identifies a positional-index precision mismatch that changes gripper commands and task success, motivating fixed-input numerical checks alongside rollout evaluation. Physical deployments on UR10e and ALOHA demonstrate robot integration, while separate delay and execution-horizon studies characterize synchronous action replay.

Method

vla.cpp separates model adapters, tensor-execution backends, and robot clients. Adapters define policy-specific graphs, backends execute their operators, and clients handle tokenization, sensing, command mapping, and action replay. Model execution runs in C++ without PyTorch.

Iterative and regression heads

Iterative policies (SmolVLA, π0, π0.5, Evo-1, GR00T N1.5/N1.6/N1.7, VLA-JEPA) refine a noise sample over T solver steps, following each checkpoint's schedule. BitVLA, OpenVLA-OFT, and VLA-Adapter regress the chunk directly. Both paths return an action chunk through one interface.

Observation reuse

Prefix computation is independent of the changing action tokens, so its features and key/value projections are cached once per observation and reused across solver steps. Model latency is approximately P + T·E. Graphs and buffers persist across requests of the same shape.

Self-contained bundles

GGUF stores weights, architecture metadata, and normalization statistics. A new policy adds an adapter, a converter, and a runtime registration. Backend coverage depends on operator support and precision.

Ternary tensor-core kernel

BitVLA's ternary weights are packed four 2-bit codes per byte, and activations are quantized row-wise to int8. The multi-row path uses IMMA tensor-core instructions in place of the dp4a CUDA-core baseline.

Numerical validation

The prediction check fixes weights, images, tokens, state, noise, masks, and schedules, then reports the maximum absolute and relative RMS error against reference actions. Intermediate tensor dumps localize any discrepancy.

Leaderboard

All eleven supported models are evaluated on LIBERO-Object with 100 episodes per model, and profiled on CUDA, Metal, and OpenVINO. Ten of the eleven reach success rates within 3.2 percentage points of their reference. GR00T-N1.6 reaches 88% against 99% for its PyTorch reference, and the cause of this gap is still unresolved. Incomplete episodes count as failures.

TensorRT comparison

A matched GR00T-N1.7 comparison on an RTX PRO Blackwell 1000 favors TensorRT, at 70.5 ms median against 130.2 ms, a 1.85x difference, with 98/100 and 96/100 successes. TensorRT is the faster option for this configuration; vla.cpp instead offers one implementation across processor backends.

Where the time goes

On an RTX 5070, vision plus backbone take 52% of execution time for SmolVLA (T=10), 52% for GR00T-N1.6 (T=4), 75% for π0 (T=10), and about 99.5% for the direct-head BitVLA. Even with cached observation features, the action expert takes nearly half the time for SmolVLA and GR00T-N1.6.

Positional-Index Precision

SmolVLA shows how a small implementation difference can change policy behavior. Its vision encoder maps patch coordinates to discrete indices that select learned position embeddings. Computing those coordinates at a different precision can push a value across an index boundary and select a different embedding.

Position-embedding error 0.32 to 0.003

Relative error after matching the half-precision reference computation.

Action difference 1.97 to <0.01

The maximum difference sits on the gripper channel and is large enough to reverse the gripper command.

LIBERO-Object task 0 2/10 to 9/10

Success on placing a soup container in a basket, once index precision matches the reference.

Numerical validation must therefore cover discrete preprocessing decisions as well as floating-point network operations. On Metal, running the vision and language towers in 32-bit cuts the fixed-input action discrepancy from 2.0e-3 to 8.3e-5, at a cost of 33 ms and 672 MiB.

Comparison

The project targets shared execution across VLA architectures and processor backends, with numerical checks and robot evaluation. Python reference stacks, quantization, and vendor compilers each solve adjacent parts of the deployment problem.

Python reference servers

Eager PyTorch dispatch leaves batch-1 VLA inference launch-bound. torch.compile closes much of the gap. Against the faster of the two on an RTX 3090, vla.cpp matches four models and is 1.18-1.84x faster on three, with no Python in the model path.

Quantization-only deployment

Weight packing controls footprint but not arithmetic cost. Packing BitVLA leaves latency unchanged; the 4.0-4.6x speedup comes from moving the same ternary math onto IMMA tensor cores.

Single-target compilers

TensorRT is 1.85x faster for GR00T-N1.7 on an RTX PRO Blackwell 1000, but it targets NVIDIA only. vla.cpp favors one bundle format and one serving path across eleven models on NVIDIA, Apple, and Intel hardware, including CPUs.
